# HPM6E 双核性能对照方法与已验证结果

## 适用范围与状态

本板HPM6E8Y、SDK1.13.0、Debug/O0、软件double、两个SV660N、1ms PDO。结果来自2026-10-12的同类动作历史记录，以及本次对0.25.1-amp/480MHz的扩大UDP实测。**本次尚未重新刷入单核300及双核300跑完整相同脚本：USB2两次打开失败，需现场恢复。** 历史小样本只能给出局部计算收益，不是完整的新A/B吞吐量结论。

## 已有同类动作的板内规划耗时

单位µs，计时为板端PTPC时间差，包含任务抢占；不是排除中断的纯算法周期数。

| 动作 | 单核300，0.24.1 | 双核300，初轮记录 | 双核480，0.25.1 | 单核300/双核480 |
| --- | ---: | ---: | ---: | ---: |
| 两轴共同周期定位：轴0 | 141 | 237 | 81 | 1.74倍 |
| 两轴共同周期定位：轴1 | 150 | 143 | 89 | 1.69倍 |
| 运动中反向改目标：轴0 | 199 | 310 | 119 | 1.67倍 |
| 运动中反向改目标：轴1 | 148 | 142 | 88 | 1.68倍 |

- 四点均值159.5→94.25µs，耗时减少40.9%，局部计算加速约1.69倍。来源为原工程`multiaxis-0.24.1/live.json`、`amp-hardware-20261012-1530/live-300.log`及`live-480.json`。
- 双核300并非全部更快，轴0单次值更慢。样本不足以分离抢占、相位和IPC影响；不能把这个均值当双核固有开销或用来夸大升频收益。
- 原始位置和执行相位并非位级一致，采样数只有每情形一次；不能给出统计置信区间或由此推算八轴容量。

## 当前480MHz扩大验证

控制发送裸函数UDP，受理应答回来源端口；相同两轴轨迹，2轮，每轮24次安静、24次并发，共96条批次、192个规划计时。

并发模式：3个HTTP轴详情请求线程、约200Hz目标的UDP反馈线程、ETH上的1kHz HTR2；同时运动中反复换向改目标。实际请求量记录在报告，目标频率不是已达到的吞吐量。

| 指标 | 安静模式 | 并发模式 |
| --- | ---: | ---: |
| 规划计时样本 | 96 | 96 |
| 规划中位数µs | 139 | 129 |
| 规划p95 µs | 442 | 336 |
| 规划最大µs | 962 | 1345 |
| UDP受理中位数ms | 1.042 | 0.981 |
| UDP受理p95 ms | 1.135 | 1.118 |
| UDP受理最大ms | 1.445 | 1.602 |

四段共10939个HTR2样本，无丢样、无无效PDO；单段周期p99最高1210µs，最大1269µs。总线timeout累计1→1，没有新增。并发共445次HTTP和348次UDP背景请求，未失败，96次批次均核验同周期交接；最后两轴取消使能、RAM通信设置恢复，未写Flash。

**解释边界**：扩大样本的轨迹、相位与上一表不同，不能把139µs与历史141µs直接相除。规划最大1345µs包含实时任务抢占；使用提前交接窗口不等于每个求解须在当前一个PDO内完成。PDO仍是1ms，没有变为0.625ms。

## 端到端时间的测量陷阱

首轮使用WS包装函数时，受理中位数约45～49ms，而裸函数UDP约1ms。可能涉及TCP发送合并/延迟ACK、网络服务和PC客户端调度；未抓包逐项定位，不能断言某一项就是根因，也不能称“CPU解析用了45ms”。

`handoff_observed_ms`是发送到HTTP轮询看到新批次的时间，包含读取时延；本轮约37～45ms，**不是板端实际交接时延**。要测精确交接，需板端受理/周期标记或对齐的PDO目标波形，不能拿PC观察代替。

## 同板可复现对照流程

仅当前授权的安全现场可执行。先确认空闲/取消使能、配置/绑定一致和镜像哈希；按单核300、双核300、双核480依次使用同一脚本，不擦配置、保持编译参数。测试后恢复已验证的480包并核验最终状态。

原工程命令示例（路径需在本机调整）：

```text
python tests/hardware/benchmark_amp.py --label single300 --firmware 0.24.1-multi --hz 300000000 --output out/validation/amp-performance-20261012/single300.json
python tests/hardware/benchmark_amp.py --label amp300 --firmware 0.25.1-amp --hz 300000000 --output out/validation/amp-performance-20261012/amp300.json
python tests/hardware/benchmark_amp.py --label amp480 --firmware 0.25.1-amp --hz 480000000 --output out/validation/amp-performance-20261012/amp480-udp.json
```

测段内不用OpenOCD halt或Flash备份。记录实际频率、设备版本、负载成功数、各轴参数、每段周期分布/有效位、受理延迟、板内规划和最终目标。改变编译优化、浮点ABI、周期、曲线容量或网页连接数须单列，不能藏在“仅升频”中。

## 开发基准建议

建议将**0.25.1-amp/双核480MHz作为当前软件开发候选基准**：局部规划约40%耗时下降，管理核与运动核分离，现有两轴并发通过；保留单核300回退及双核300对照。

不能宣布整体应用获得3.2倍性能，也不能宣称双核本身使每条轨迹计算翻倍。理想单串行CPU升频比1.6，总核心频率比3.2只是无调度/共享瓶颈的上界参考。正式生产基准仍需完整同脚本A/B、长期电气/温升、八轴、真实带载和最坏时延验收。
